## 1. Overview
This document defines how generated project files are stored, indexed, versioned, and exported — the data layer beneath the Workspace UI (`31-workspace.md`) and `WorkspaceService` (`22-services.md`).

---

## 2. Workspace Storage

```
interface FileStorageAdapter {
    FileTree listTree(UUID projectId);
    String readFile(UUID projectId, String path);
    void writeFile(UUID projectId, String path, String content);
    void deleteFile(UUID projectId, String path);
    void moveFile(UUID projectId, String fromPath, String toPath);
}
```

| Adapter | Used In | Storage Location |
|---|---|---|
| `LocalFileStorageAdapter` | Local dev, single-instance Docker deployment | `{workspace_path}` on local disk (per `projects.workspace_path`, `03-database.md`) |
| `S3FileStorageAdapter` | Multi-instance cloud deployment | Object storage (S3-compatible), keyed by `projectId/path` |

Adapter selection is configuration-driven (`storage.adapter: local|s3` in `application.yml`), consistent with the abstraction pattern used for `AIProvider` (`07-ai-orchestration.md`) — application code never branches on storage backend.

## 3. File Indexing
- Each project maintains a lightweight in-database file index (`workspace_files` — extends `12-er-diagrams.md`) mirroring the storage backend's actual tree, used for fast listing without round-tripping to object storage on every Explorer render:

```sql
CREATE TABLE workspace_files (
    id UUID PRIMARY KEY,
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    file_path VARCHAR NOT NULL,
    file_type VARCHAR,
    size_bytes INT,
    purpose TEXT,
    last_modified TIMESTAMP,
    UNIQUE (project_id, file_path)
);
```
- The index is the same data surfaced as `FILE`-type `project_memory` entries (`08-memory.md`); `workspace_files` is the queryable/indexed form, `project_memory` carries the richer "purpose/dependencies" narrative. The Memory Module writes both on file creation in a single transaction to avoid drift.
- Re-sync job (`25-background-jobs.md`) reconciles the index against actual storage nightly, defending against drift from any out-of-band write.

## 4. Project Versions
- Every significant generation/edit run produces a snapshot recorded in `project_versions` (`12-er-diagrams.md`): a `snapshot_path` pointing to a compressed archive of the workspace at that point, plus a human-readable `change_summary` (generated by `DocumentationAgent`, `26-agent-design.md`).
- Snapshots are **incremental** in storage (only changed files are duplicated; unchanged files reference the prior version's blob) to avoid linear storage growth per version — implemented via content-addressed storage (hash-based file naming) under the hood.
- Version history is browsable via `GET /api/v1/projects/{id}/versions` (`04-api-design.md`) and rendered in `ProjectExplorer` (`17-pages.md`).


## 5. Downloads
- `GET /api/v1/workspace/{id}/download` (extends `04-api-design.md`) streams a zip archive of the current workspace state, assembled on-demand from the storage adapter (not pre-built, to always reflect the latest saved state).
- Large projects stream the zip rather than buffering fully in memory, to bound backend memory usage regardless of project size.
- Downloads are rate-limited per user (`24-security.md`) to prevent abuse of the archive-assembly endpoint.

---

## 6. Security Considerations
- All file paths are canonicalized and validated against the project's workspace root before any read/write/delete, preventing path traversal (`24-security.md` §5).
- File content size is capped (default 5MB/file) to prevent storage abuse via a single oversized "file."
- Downloads and reads always re-verify project ownership server-side, never trusting a client-supplied `projectId` alone.

---

## 7. Implementation Notes
- `WorkspaceService` is the only caller of `FileStorageAdapter` — no other module touches workspace storage directly, keeping the storage abstraction boundary clean per `21-backend-architecture.md`.
- File writes from agents (`26-agent-design.md`) and file writes from direct user edits (Monaco save) go through the identical `writeFile` path, ensuring indexing/versioning triggers consistently regardless of the write's origin.

## 8. Future Considerations
- Per-file diff-based versioning (rather than whole-snapshot deltas) for finer-grained history once storage costs or user demand justify the added complexity.
- Configurable retention policy for old versions (auto-prune beyond N versions or M days) as a project-level setting.
